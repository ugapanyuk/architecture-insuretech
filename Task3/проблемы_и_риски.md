# Анализ проблем и рисков текущей архитектуры InsureTech

Текущая архитектура, основанная на синхронных REST-взаимодействиях для обмена данными между сервисами, несет в себе ряд существенных проблем и рисков, которые будут усугубляться с ростом количества партнеров и нагрузки.

## 1. Сильная связанность компонентов 

*   **Проблема:** Сервисы-потребители (`core-app`, `ins-comp-settlement`) напрямую зависят от доступности и контракта API сервиса-продюсера (`ins-product-aggregator`). Аналогично, `ins-comp-settlement` зависит от API `core-app`.
*   **Риски:**
    *   **Сложность внесения изменений:** Любое изменение в API `ins-product-aggregator` потребует одновременного обновления и переразвертывания всех сервисов-потребителей, что усложняет и замедляет цикл разработки.
    *   **Низкая автономность команд:** Команды, отвечающие за разные сервисы, не могут работать независимо друг от друга.

## 2. Каскадные сбои 

*   **Проблема:** `ins-product-aggregator` выполняет синхронные "веерные" запросы к API пяти страховых компаний.
*   **Риски:**
    *   **Низкая отказоустойчивость:** Если хотя бы один из внешних API страховых компаний отвечает медленно или недоступен, весь агрегационный запрос в `ins-product-aggregator` задерживается или завершается ошибкой.
    *   **Цепная реакция:** Ошибка в `ins-product-aggregator` немедленно передаётся вызывающему сервису (`core-app` или `ins-comp-settlement`), что может привести к сбою в его работе и, в конечном итоге, к ошибке для конечного пользователя. Надежность системы начинает определяться ее самым ненадежным внешним партнером.

## 3. Неэффективность и задержки из-за поллинга

*   **Проблема:** Сервисы `core-app` и `ins-comp-settlement` вынуждены периодически опрашивать с помощью механизма поллинга (`poll`) `ins-product-aggregator`, чтобы получить обновления. Аналогично `ins-comp-settlement` опрашивает `core-app`.
*   **Риски:**
    *   **Неактуальные данные (Stale Data):** Между опросами данные в локальных репликах устаревают. Например, `core-app` может работать с неактуальными тарифами до 15 минут, что может привести к неверным расчетам для клиента.
    *   **Избыточная нагрузка:** Большинство поллинговых запросов выполняются впустую, так как данные не меняются. Это создает ненужную нагрузку на сеть и на опрашиваемые сервисы.
    *   **Пиковые нагрузки:** Ежесуточный запрос от `ins-comp-settlement` к `core-app` для получения всех страховок за день создает кратковременную, но высокую нагрузку на `core-app` и его базу данных.

## 4. Плохая масштабируемость

*   **Проблема:** Текущая модель синхронной агрегации не масштабируется.
*   **Риски:**
    *   **Деградация производительности:** Подключение ещё пяти страховых компаний удвоит количество одновременных синхронных запросов в `ins-product-aggregator`. Это гарантированно приведёт к увеличению времени ответа и повышению вероятности сбоя всего агрегационного запроса. Система в её текущем виде не выдержит такого роста.

## Вывод

Для преодоления проблем необходимо переходить к асинхронной модели взаимодействия.
