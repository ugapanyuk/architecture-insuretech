# Задание 1. Проектирование технологической архитектуры

Существующая архитектура имеет несколько единых точек отказа и не рассчитана на горизонтальное масштабирование и географическое распределение, что и вызывает проблемы, приведенные в условии задания.

**Схема целевой архитектуры приведена в файле InureTech_технологическая_архитектура_to-be.drawio** [а также для удобства в файле png.](./InureTech_технологическая_архитектура_to-be.png)


### Ключевые архитектурные решения:

1.  **Переход к нескольким зонам доступности.** Это основное изменение для обеспечения высокой доступности (99,9%) и выполнения требований по RTO/RPO. Все критически важные компоненты системы будут развернуты как минимум в двух независимых зонах доступности.

1.  **Архитектура Kubernetes:**
    *   **Независимые кластеры в каждой зоне доступности.** Вместо одного кластера будет развернуто по одному независимому кластеру Kubernetes в каждой зоне доступности. Этот подход выбран как более надежный: отказ одной зоны или проблемы в сети между зонами не повлияют на работоспособность в другой зоне. 
    *   **Горизонтальное автомасштабирование (HPA).** Для каждого сервиса будет настроен Horizontal Pod Autoscaler, который будет автоматически увеличивать или уменьшать количество подов в зависимости от нагрузки (CPU/Memory), что позволит гибко реагировать на пиковые нагрузки.

1.  **Средства мониторнига.** Средства мониторинга (Prometheus, Grafana, ELK) будут общими для всех зон доступности.
  
1.  **Глобальная балансировка и отказоустойчивость:**
    *   **Cloud DNS:** Будет использоваться для управления трафиком на глобальном уровне. С помощью health-check'ов он будет автоматически направлять трафик пользователей в работоспособную зону, обеспечивая автоматическую отработку отказа.
    *   **CDN (Content Delivery Network):** Для ускорения загрузки статических файлов веб-приложения (JS, CSS, изображения) для пользователей из любых регионов. Это решит проблему разного времени загрузки в зависимости от географии.
       
5.  **Конфигурация базы данных PostgreSQL:**
    *   **Managed Service for PostgreSQL:** Для упрощения администрирования и обеспечения отказоустойчивости будет использоваться управляемый сервис баз данных.
    *   **Multi-AZ конфигурация с синхронной репликацией:** Кластер БД будет состоять из Мастера в одной Зоне Доступности и как минимум одной синхронной реплики в другой. Это гарантирует RPO, близкий к нулю (RPO=0) в случае отказа одной зоны, так как транзакция не будет подтверждена, пока не запишется на реплику.
    *   **Резервное копирование:** Будут настроены автоматические инкрементальные бэкапы с заданной периодичностью (например, каждые 15 минут) в отдельное гео-распределенное объектное хранилище. Это обеспечит выполнение требования RPO=15 мин даже в случае полного отказа региона.
6.  **Шардирование БД:** На текущем этапе при объеме данных в 50 GB шардирование не требуется. Оно значительно усложняет архитектуру и логику приложения. Текущие проблемы производительности решаются за счет горизонтального масштабирования приложения, введения кэширования и использования реплик БД для чтения.
7.  **Внедрение кэширования:** Для снижения нагрузки на базу данных и ускорения ответов будет внедрен распределенный кэш (например, Managed Redis), также в Multi-AZ конфигурации. В кэш будет вынесена часто запрашиваемая, редко изменяющаяся информация (тарифы, условия продуктов).
